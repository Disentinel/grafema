## 1. Тезис

«Граф» в RFDB — это не модель данных, а **физическая раскладка, протёкшая в логическую модель**.
Узел — семиполевая запись `NodeRecordV2 { semantic_id, id, node_type, name, file, content_hash,
metadata }` (`packages/rfdb-server/src/storage_v2/types.rs:388-402`), ребро —
`EdgeRecordV2 { src, dst, edge_type, metadata }` (`types.rs:412-421`). В оперативной памяти факт
уже n-арен — `pub type Fact = Box<[Value]>` (`derive/value.rs:20`), — но на границе стора стоит
арность-замок: только 2+meta для рёбер и 3+meta для узлов, с кодированными аборта́ми `E-MAT-002`
и `E-MAT-009` (`derive/materialize.rs:50-51`, `:311-320`). Провенанс по факту не хранится
принципиально (`derive/exec.rs:243-252`), а «авторство» и «поколение» контрабандой едут внутри
JSON-блоба как `_source`/`_generation`.

Следствия этой протечки не гипотетические, и их четыре класса:

1. **Диспетчеризация вместо модели.** `attr(N,K,V)` в обратную сторону разваливается на ПЯТЬ
   рукописных ветвей, ТРИ из которых — O(n)-сканы всего множества узлов
   (`datalog/eval.rs:1561-1589`: `"id"` → парс, `"semantic_id"` → `find_by_attr(default)` + фильтр,
   `"version"` → то же по полю, которое `engine_v2.rs:39` жёстко зашивает константой `"main"`,
   `name if name.contains('.')` → `reverse_metadata_scan`, `_` → индексный путь). Доккомментарий
   `:1583-1584` сам называет режим отказа «a silent forward/reverse asymmetry».
2. **Обходы контракта в проде.** Шесть продакшн-энричеров обходят `BatchHandle.commit()` стороной,
   потому что удаление по `file` уничтожает аддитивные записи
   (`packages/util/src/enrichers/libraryCallbackEnricher.ts:95-98` и пять других).
3. **Замкнутые списки в горячем коде.** Планировщик знает ровно пять базовых отношений —
   `const BASE_RELATIONS: &[&str] = &["node","type","edge","incoming","attr"]` (`derive/plan.rs:927`),
   а `build-once` хеш-джоин исполнителя диспетчеризуется **по строковому имени предиката**
   (`derive/exec.rs:2012-2021`). При этом реальная база уже несёт **141 различный предикат**
   (MEASURED, §6.2).
4. **Молчаливый выбор при конфликте.** Два автора, утверждающих разное об одной сущности, сегодня
   разрешаются порядком физического хранения: `get_node_at` берёт первый хит в L0 в порядке
   newest→oldest, затем L1 (`storage_v2/multi_shard.rs:852-895`). MEASURED: на реальной базе таких
   конфликтов **39, и все 39 расходятся и по `node_type`, и по `file`, и по `_source`** (§2.3).

**Этот документ специфицирует раз-протечку.** Истина становится множеством фактов с ключом
`(perspective, predicate, tuple)` и пер-ассершн метаданными; граф Grafema становится **видом**
(covering index) над атрибутными предикатами сущности; физическая раскладка объявляется
**пер-предикатной стратегией**, а не свойством логической модели.

## 2. Модель фактов (нормативно)

### 2.1. Два уровня идентичности — факт и ассершн

Самое острое место всей миграции и единственное расхождение с формулировкой брифа, которое
пришлось **уточнить, а не принять**. Бриф говорит: «каждый атрибут — отдельный ассершн со своим
author/tick/perspective». ROFL v0 говорит другое: два разных автора, утверждающих один и тот же
кортеж, дают **ОДИН** `FactRec` — `Store.add()` возвращает `false` при коллизии ключа и мутирует
только флаг `base` (`/tmp/rofl-v0/src/store.ts:41-48`). Автор в v0 — это многозначное **побочное
отношение** над реифицированным фактом (`asserted_by($fact(...), Who)`, `reflect.ts:244-249`).

Если положить author/tick в ключ, ломается `boot.rofl:33-34`:
`forged[audit](F) :- asserted_by(F,Who), in_perspective(F,P), not authority(P,Who)` — сегодня один
факт может быть одновременно подделанным и легитимным (два автора, один кортеж); с автором в ключе
это перестаёт быть выразимым. Это семантическая вилка с оракулом.

**НОРМАТИВНОЕ РЕШЕНИЕ: двухуровневая идентичность.**

| Уровень | Идентичность | Что это | Соответствие v0 |
|---|---|---|---|
| **Fact** | `fid = BLAKE3(canon(perspective, predicate, tuple))[0..16] LE` | логический факт; то, что видит правило, запрос и канонический хеш | ≡ `factKey()` `store.ts:25-27`, но бинарно, а не строкой |
| **Assertion** | `aid = BLAKE3(fid ‖ author_u32 ‖ tick_u64)` | одно утверждение факта одним автором на одном тике | ≡ элемент `firings`-множества `store.ts:33`; `supportCount()` `store.ts:131` = число ассершнов |

Множество ассершнов над одним `fid` — это ровно `supportCount` из v0, который там существует
единственно ради корректности `excise` при множественной поддержке (`LIMITS.md:11-13`). То есть
пер-ассершн гранулярность **не является отклонением от v0** — она является материализацией
структуры, которую v0 уже держит в боковой карте, но не хранит.

Гранулярность атрибутов при этом сохраняется полностью и является тем самым «самым острым
изменением» из брифа: `name`, `file`, `node_type` сегодня делят ОДНУ строку и ОДИН провенанс;
после миграции это три разных `fid`, каждый со своим множеством ассершнов, каждый supersede-ится
независимо. Половину записи сегодня заменить нельзя — после миграции можно.

### 2.2. Нормативная форма записи — и почему ассершн НЕ самодостаточен

```rust
/// Логический факт. Идентичность = содержимое. Дублей по построению нет.
pub struct FactKey {
    pub perspective: PerspectiveId,   // u32, интернируется в каталоге
    pub predicate:   PredicateId,     // u32, интернируется в каталоге
    pub tuple:       Box<[Value]>,    // n-арный; арность-замка НЕТ
}
// fid: u128 = blake3(canon(perspective, predicate, tuple))[0..16] LE

/// Одно утверждение факта. Множество ассершнов на один fid — норма, не ошибка.
/// НЕ САМОДОСТАТОЧЕН: не несёт кортежа. Всегда парен с FactKey (см. ниже).
pub struct Assertion {
    pub fid:            u128,
    pub author:         AuthorId,     // u32, интернируется; сегодня = metadata["_source"]
    pub tick:           u64,          // сегодня = metadata["_generation"]
    pub tag:            TagV2,        // semiring; types.rs:428-511
    pub tx_created:     u64,
    pub tx_invalidated: u64,          // TX_OPEN = u64::MAX; КЭШ, не истина (§2.4)
}
// aid: u128 = blake3(fid ‖ author ‖ tick)
```

**Исправление rev 1.0 (блокер ревью).** В rev 1.0 трейт стора возвращал `Iterator<Item = Assertion>`.
Это неисполнимо: `Assertion` не несёт кортежа, а `fid` — односторонний хеш, из него кортеж
не восстанавливается. Нормативно:

```rust
/// Единица чтения. Кортеж ВСЕГДА едет вместе с ассершнами, декодированный
/// из колонок сегмента по арности и типам из PredicateDecl.
pub struct FactRow {
    pub key:        FactKey,          // perspective + predicate + tuple, декодированы
    pub fid:        u128,
    pub assertions: SmallVec<[Assertion; 2]>,   // ВСЕ живые ассершны этого факта в снапшоте
}
```

Байты кортежа хранятся физически (колонки сегмента), `PredicateId` в заголовке сегмента даёт арность
и типы колонок для декодирования, и на трейте есть обратный примитив
`fn tuple(&self, s: &Snapshot, fid: u128) -> Option<Box<[Value]>>` — он нужен рефлексии (§2.7) и
объяснению вывода (`derive/exec.rs:248` `DerivationWitness`), которым `fid` приходит как значение.

Все четыре пер-ассершн поля **уже определены в формате** и уже имеют посчитанную ширину:
`ProvenanceV2 { rule_ast_hash: u32, generation: u64 }` = `PROVENANCE_RECORD_SIZE = 12`
(`storage_v2/writer.rs:17`), `TAG_DIR_RECORD_SIZE = 2+2+4 = 8` (`writer.rs:19`),
`TX_RECORD_SIZE = 8+8 = 16` (`writer.rs:21`). Итого 36 B/ассершн — это не изобретённая цифра,
это ширина, которую формат уже объявляет. Новым является только `perspective` (4 B, интернированный
u32) — у него аналога нет.

**КРИТИЧЕСКАЯ ОГОВОРКА (MEASURED, Discovery 3):** эти колонки пишутся ТОЛЬКО через
`writer.add_derived` (переключает писателя на `FORMAT_VERSION_DERIVED = 3`, `writer.rs:36`), а
продовый flush зовёт `writer.add(...)` (`storage_v2/shard.rs:899`, `:938`). На реальной 543 MB базе
Grafema **359/359 сегментов несут магию `SGV2` версии 2**. То есть форма правильная, но **ни одного
продового байта через этот путь не прошло**. Это одновременно главный аргумент «за» (ничего не надо
изобретать) и главный источник неуверенности (нулевой полевой пробег) — см. §11 O-12.

### 2.3. Функциональные предикаты — недостающий класс (НОВОЕ в rev 2.0)

Ревью «сломай абстракцию» нашло класс, которого в rev 1.0 не было, и нашло его на реальных данных,
а не рассуждением. Модель rev 1.0 утверждала: контент-адресация устраняет дубли по построению, два
автора одного кортежа дают один факт с двумя ассершнами. Это верно — и **ровно поэтому ломается на
предикатах, у которых субъект допускает только ОДНО значение**.

**MEASURED, команда и вывод инлайном:**

```
$ cd /tmp/rofl-measure && python3 dupnodes.py
distinct node ids: 503404
ids with >1 record: 39
  conflicting node_type : 39
  conflicting name      : 0
  conflicting file      : 39
  conflicting _source   : 39

sample:
id=23255204425269720720995687792899350232
    type=GLOBAL_DEFINITION    name='notElem'   file='<runtime/haskell>'
    type=EXTERNAL_FUNCTION    name='notElem'   file='__grafema_virtual/haskell-local-refs'
```

Тридцать девять сущностей реальной базы несут по две записи, и **все 39 расходятся одновременно по
`node_type`, по `file` и по автору**. Сегодня выбор делает физика: `get_node_at`
(`storage_v2/multi_shard.rs:852-895`) идёт по L0 в порядке newest→oldest (`:860` `.iter().rev()`) и
возвращает первый хит, затем то же по L1 (`:878`). Это не политика — это порядок сегментов.

В модели rev 1.0 оба факта — `node_type(E,"GLOBAL_DEFINITION")` и `node_type(E,"EXTERNAL_FUNCTION")` —
имеют РАЗНЫЕ `fid` (кортежи различны), оба живы, оба корректны, и **правила выбора нет**. Любой
потребитель, ожидающий один тип у сущности (а это `NodeView`, §3.3), получит недетерминированный
ответ или два ответа. Это не крайний случай — это молчаливая потеря функциональности.

Тот же класс — не единичный. Три независимых места продакшна уже держат рукописный тай-брейк
ровно этой формы:

| # | Место | Как разрешает сегодня |
|---|---|---|
| 1 | `storage_v2/multi_shard.rs:852-895` (`get_node_at`) | первый хит L0 newest→oldest, потом L1 |
| 2 | `grafema-orchestrator/src/layout/loader.rs:224-228` | `tracing::warn!("duplicate RFDB id across placeable types — keeping first")` |
| 3 | `derive/materialize.rs:53-57` | доккомментарий дословно: *«two derived facts that agree on the endpoints but differ in a meta column are ONE edge — which fact's metadata lands is storage-order-defined, not specified»* |

Три места, один и тот же режим отказа, ни одного объявленного правила. **Это и есть недостающий
класс.** Модель обязана его назвать, а не рационализировать.

**НОРМАТИВНО: кардинальность — свойство предиката, объявляемое в каталоге.**

```rust
pub enum Cardinality {
    /// Субъект (key_cols) допускает ЛЮБОЕ число различных значений остальных колонок.
    /// Дефолт для открытого пространства. Пример: edge-предикаты, `tag`, `doc_note`.
    MultiValued,
    /// Субъект допускает РОВНО ОДНО живое значение в одной перспективе.
    /// Пример: node_type, file, sid, name, line, column.
    Functional,
}
```

`PredicateDecl.cardinality` (§3.1). Дефолт — `MultiValued`: объявление функциональности — явное
действие, потому что оно **ограничивает** истину.

**Нормативный порядок разрешения функционального конфликта** (применяется на ЧТЕНИИ, не на записи —
хранилище остаётся монотонным и хранит оба факта):

1. **Приоритет автора.** Каталог несёт частичный порядок `author_priority: Vec<AuthorId>` на
   предикат. Ассершн автора с бо́льшим приоритетом побеждает. Если оба автора вне таблицы или равны —
   шаг 2.
2. **Максимальный `tick`.** Более позднее утверждение побеждает. Ничья — шаг 3.
3. **Минимальный `fid`.** Тотальный, детерминированный, независимый от раскладки, шардирования и
   порядка сегментов тай-брейк. Он ОБЯЗАН быть последним шагом, иначе §9 не имеет права называть
   свой хеш каноническим.

**Конфликт не проглатывается — он материализуется.** При каждом разрешении шага 2 или 3 (то есть
когда приоритет автора НЕ разрешил спор) стор порождает факт

```
conflict(Subject, PredicateId, WinnerFid, LoserFid, Tick)
```

в перспективе `audit`. Это прямой аналог `forged[audit]` из `boot.rofl:33-34`: конфликт становится
запрашиваемым фактом, а не логом. Тридцать девять измеренных случаев дадут 39 таких фактов — и это
**первый раз, когда они станут видимы**, а не растворятся в порядке сегментов.

**Аборт вместо тишины на границе батча.** Если ОДИН автор в ОДНОМ батче утверждает два различных
значения функционального предиката об одном субъекте — это не конфликт мнений, это баг производителя.
Коды: `E-FUNC-001` (интра-батч двойное утверждение функционального предиката). Класс аборта тот же,
что у `E-MAT-002` / `E-EXEC-001` (`derive/exec.rs:132-142`) — до коммита, а не после.

**Что это меняет в остальном документе:**

- Критерий C1 (§10.5) перестаёт быть «побайтовый round-trip» — он становится «побайтовый round-trip
  ПОСЛЕ функционального разрешения», и обязан отдельно отчитаться о 39 узлах.
- `NodeView` (§3.3) определяется только над функциональными предикатами. Это делает его корректным
  видом, а не «одним из возможных».
- Три тай-брейка выше получают названного преемника: (1) → правило §2.3, (2) → правило §2.3 плюс
  `conflict`-факт вместо `warn!`, (3) → K-2 (§4.1 B-2), где `meta` входит в идентичность и конфликт
  исчезает как класс.

### 2.4. Supersession: логика — истина, физика — кэш

| Уровень | Механизм | Где живёт | Авторитетность |
|---|---|---|---|
| Логический | факт `supersedes(aid_new, aid_old)` в предикатном пространстве | обычный бинарный факт `Id×Id` | **ЕДИНСТВЕННЫЙ ИСТОЧНИК ИСТИНЫ** |
| Физический | `tx_invalidated` на ассершне | колонка сегмента, `TX_RECORD_SIZE=16` | **КЭШ**. Никогда не авторитетен |

**Исправление rev 1.0 (блокер ревью).** rev 1.0 писала «физический уровень производен от
логического», но при этом §9.1 определяла живость факта как `tx_invalidated == TX_OPEN`. Это
циклично: если логика — истина, то живость обязана определяться логикой, иначе supersede-факт,
пришедший ПОСЛЕ компакции, не будет иметь эффекта, а канонический хеш разойдётся между двумя
физически различными, логически одинаковыми базами.

**Нормативное определение живости (единственное):**

> Ассершн `a` **жив** в снапшоте `S` ⟺ в `S` НЕТ живого факта `supersedes(_, aid(a))`.
> Факт `f` **жив** ⟺ жив хотя бы один его ассершн.

Определение рекурсивно и корректно: `supersedes` — обычный предикат, его собственные ассершны
подчиняются тому же правилу; цикл `supersedes(x,y), supersedes(y,x)` невозможен, потому что `aid`
содержит `tick`, а supersede-ассершн обязан иметь `tick` строго больший, чем у superseded (проверка
на границе стора, код `E-SUP-001`).

`tx_invalidated` — оптимизация: компакция, обнаружив живой `supersedes(_, aid)`, вписывает
`tx_invalidated` в строку, чтобы последующие чтения не платили за join. Правила его использования:

1. `tx_invalidated != TX_OPEN` ⟹ ассершн мёртв (кэш никогда не даёт ложно-мёртвых: он ставится
   только по уже установленному факту supersession).
2. `tx_invalidated == TX_OPEN` ⟹ **ничего не значит**; требуется join с `supersedes`.
3. Ни один читатель НЕ имеет права заключить «жив» только по `tx_invalidated`.

Стоимость правила названа честно: **живость требует anti-join с `supersedes` на каждом чтении**.
Поэтому трейт (§7.2) несёт её как явный примитив `live_filter`, а не прячет: `supersedes` объявлен
`Adjacency` с обратным раном по `c1`, так что anti-join — это префиксный зонд по `aid`, а не скан.
На сегодняшнем графе `supersedes` пуст, поэтому холодная стоимость нулевая; в режиме χ=1.0, H=10
(§6.4) он вырастает до размера базы, и anti-join становится доминирующим — это входит в U-6.

Логический уровень — прямая калька того, как supersession реально делался в 24-часовом прогоне v0:
целиком в объектном языке, через отрицание над монотонным стором. Дословно, `run/rounds/round-003.rofl:7-11`
(ветка ⟨R⟩, см. Приложение):

```prolog
decision[a](reattach(slow, depth_level)).
-- audit extension (v0.2+r3): a miscast with a superseding reattachment to a
-- registered level is `readdressed`; the live audit target becomes open_miscast.
readdressed[audit](P, L) :- miscast[audit](P, L), decision[a](reattach(P, L2)), level(L2).
open_miscast[audit](P, L) :- miscast[audit](P, L), not readdressed[audit](P, L).
```

Так сделано, потому что **в ядре v0 supersession не существует вовсе:**

```
$ grep -rn "supersed" /tmp/rofl-v0/src /tmp/rofl-v0/boot.rofl | wc -l
0
```

В ядре есть только разрушающее удаление: `Store.remove()` (`src/store.ts:67-79`) и
`Rofl.retract()` (`src/api.ts:146-165`). «Assert-only revision» — это **дисциплина уровня
протокола** (`run/PROTOCOL.md:43`, дословно: *«Assert-only revision: never retract a belief;
supersede it (the amnesia lesson)»*), а не механизм.

**Это означает: пункт 3 брифа («deletion заменяется supersession») — не конформанс с v0, а
РАСШИРЕНИЕ.** Документ это признаёт: см. §11 O-1 (`excise`).

### 2.5. Домен значений — и решение по bignum

Сегодня: `Value::{ Id(u128), Str(String), Int(i64), Float(f64) }` (`derive/value.rs`, теговые
константы `TAG_ID` и далее с `:29`).

Discovery 4 поправил рамку задачи: **записанный инцидент 2^68 — это стена v0 на 2^53**, а не стена
RFDB. v0 держит целые как JS `number` (f64): `{k:'i'; v: number}` (`/tmp/rofl-v0/src/unify.ts:6`),
`LIMITS.md:49-51` «no bignums (safe-integer JS range)». RFDB с `i64` доходит до 2^63 — то есть
**RFDB сегодня лучше оракула, а не эквивалентен ему**. Обе реализации падают на 2^68; в v0 это
обошли атомом-заглушкой `verified_to_2pow68` (`run/collatz-models.rofl:10-11`:
`ground[a](collatz, verified_to_2pow68).` / `evidence[world](collatz, verified_to_2pow68).`) —
то есть факт из литературы внесли РУКАМИ, потому что вычислить его субстрат не мог. Отчёт прогона
ставит bignum четвёртым по полезности пунктом (`run/TESTDRIVE.md:128-129`: *«bignum (#3) — Коллатц
упёрся в 2^53 на первой же неделе жизни задачи; любая теоретико-числовая нагрузка упрётся так же»*).
i128 не решает задачу — это просто более далёкая стена.

**НОРМАТИВНО:**

| Вариант | Ширина | Правило |
|---|---|---|
| `Int(i64)` | 8 B | остаётся быстрым путём. MEASURED: все числовые атрибуты графа (line/column/offset) в него влезают |
| `BigInt(Arc<[u8]>)` | var | НОВЫЙ. Произвольная точность, каноническое кодирование = минимальное two's-complement big-endian |
| `Float(f64)` | 8 B | остаётся, но **канонизируется**: любой NaN → один quiet-NaN, `-0.0 → +0.0` |
| `Id(u128)`, `Str` | 16 B / интерн | без изменений |
| `Term(Arc<TermBlob>)` | var | НОВЫЙ, §2.7 — правила и реифицированные структуры как значения |

**Правило канонизации (load-bearing для §9):** любое `BigInt`, влезающее в `i64`, ОБЯЗАНО быть
представлено как `Int(i64)`. Без этого правила два «равных» числа дают два разных `fid`, и
контент-адресация ломается молча. То же для `Float`: без канонизации NaN/`-0.0` контент-адрес
недетерминирован. Оба правила проверяются на границе стора кодом `E-VAL-001` (несканонизированный
BigInt) и `E-VAL-002` (неканонический Float).

**Цена bignum: 0 байт на измеренном графе** — из-за правила канонизации ни один из измеренных
2 108 806 числовых атрибутов не меняет представления.

**Отдельно: id-значные строки.** MEASURED — на реальной базе 20 709 метаданных-полей содержат
десятичное u128, то есть ссылку на сущность, закодированную строкой:

```
$ cd /tmp/rofl-measure && python3 idmeta.py
    ('ISSUE', 'source_node') 20570
    ('mcp:tool', 'handler_function_id') 56
    ('vscode:command', 'anchorCall') 40
    ('cli:command', 'anchorCall') 39
    ('mcp:tool', 'anchorCall') 4
```

В фактовой модели это `Value::Id`, а не `Value::Str`, и предикаты `source_node/2`,
`handler_function_id/2`, `anchorCall/2` получают стратегию `Adjacency` (§3.1) — то есть **20 709
скрытых рёбер становятся рёбрами**. Это не миграционная работа, это решение конвертера (§10.3), и
без него они останутся строками и потеряют обратный ран.

### 2.6. Реестр сущностей (entity roster) — и почему он бесплатен

`node_exists` — первоклассный предикат, и **федеративный фронтир определён через него**:
ребро, у которого `node_exists(neighbor)` ложно, становится кортежем фронтира, а не шагом обхода
(`graph/traversal.rs:129-142`). В чистой модели фактов ребро-факт на неизвестный `Id` совершенно
корректно, поэтому «существование» обязано стать явно утверждаемым фактом, иначе фронтир **молча
станет пустым** — потеря способности без ошибки компиляции.

**НОРМАТИВНО: реестром является предикат `sid`.** Сущность `E` существует в перспективе `P` ⟺
существует живой факт `sid(E, "<semantic-id>")` в `P`. Дополнительного факта `entity(E)` НЕТ.
Обоснование: `sid` всё равно обязателен (BLAKE3 односторонний — отображение `id → semantic_id`
нельзя вычислить, его надо хранить), значит роль реестра он несёт бесплатно.
`sid` объявляется `Functional` (§2.3) и получает обратный ран (§6.3).

### 2.7. Правила как данные, рефлексия (НОВОЕ в rev 2.0)

Ревью справедливо указало: rev 1.0 специфицировала стор фактов и умолчала о том, что в ROFL
**правила — это тоже факты**. В v0 это не украшение, а несущая конструкция: `encodeRule`/`decodeRules`
(`/tmp/rofl-v0/src/reflect.ts:148-177`, `:181`) кладут правило в стор термом, `boot.rofl:1-40` —
мета-ядро, которое аудирует само себя, читая ПРАВИЛА как данные. Без этого `forged[audit]`,
`leak[audit]` и весь само-аудиторский слой невыразимы, а «среда исполнения для аудируемых
рассуждений» превращается в базу графов с провенансом.

**НОРМАТИВНО:**

1. Домен значений получает `Value::Term(Arc<TermBlob>)` (§2.5). `TermBlob` — каноническое бинарное
   кодирование терма ROFL (функтор + арность + аргументы, рекурсивно). Каноническое ⟹ участвует в
   `fid` наравне с остальными значениями и не требует особого случая в §9.
2. **Правила живут в пространстве фактов, не в каталоге.** Каталог (§3.1) держит только ФИЗИКУ —
   стратегию, сорт-ключ, кардинальность, semiring, статистику. Логика (правила, их провенанс,
   их авторство) — обычные факты обычных предикатов. Это единственный способ сохранить свойство
   v0: «изменить правило = утвердить факт», без второго механизма версионирования.
3. Нормативный список рефлексивных предикатов, которые обязаны существовать (имена совпадают с v0
   ради переносимости корпуса):

| Предикат | Арность | Смысл | Соответствие v0 |
|---|---|---|---|
| `rule(RuleId, Term)` | 2 | правило как терм | `encodeRule` `reflect.ts:148-177` |
| `asserted_by(Fid, Who)` | 2 | автор ассершна как ФАКТ (вид над колонкой `author`) | `reflect.ts:244-249` |
| `in_perspective(Fid, P)` | 2 | вид над колонкой `perspective` | `boot.rofl:33` |
| `derived_by(Fid, RuleId, Tick)` | 3 | провенанс вывода | `reflect.ts:112-114` |

строит `factTerm(rel, persp, args)` и кладёт его аргументом в `in_perspective`/`asserted_by`;

каждом выводе: `src/engine.ts:302-307` эмитит `derived_by(factTerm(...), ruleId, tick)`.

Цена названа самим прогоном (`run/SUBSTRATE_ISSUES.md:41-49`, заголовок раздела дословно —
*«#5 — Track A memory wall: provenance doubles the store»*): *«Measured: k=14 → 590,838 facts /
70.9s. Facts grow ~x2.1 per k … the honest ceiling for in-substrate Terras classification is k≈16

### 2.8. Временна́я область: tick, timeless, as_of (НОВОЕ в rev 2.0)

v0 несёт `scope: 'timeless' | 'tick'` на факте (`/tmp/rofl-v0/src/store.ts:6`, `:12`) и
**немонотонный** `advanceTick`, который сносит tick-scoped факты. rev 1.0 упомянула это одной
строкой в таблице сверки и не специфицировала — ревью справедливо назвало это дырой, потому что
монотонный стор без определения области времени не может воспроизвести ни один tick-scoped вывод v0.

**НОРМАТИВНО: `scope` — свойство ПРЕДИКАТА, объявляемое в каталоге, а не свойство факта.**

```rust
pub enum TemporalScope {
    /// Факт истинен вне времени. `tick` ассершна — только провенанс.
    /// Дефолт. Все сегодняшние графовые предикаты — Timeless.
    Timeless,
    /// Факт истинен ТОЛЬКО на своём тике. Запрос на тике t видит только ассершны с tick == t.
    Ticked,
}
```

Обоснование выбора «на предикате, а не на факте»: физическая раскладка объявляется пер-предикатно
(§3.1), а `Ticked`-предикат требует `tick` в сорт-ключе. Смешивать два режима внутри одного рана —
значит потерять префиксный зонд. Это отклонение от v0 (там `scope` на факте) и оно названо: §11 O-4.

**`advanceTick` не переносится.** Немонотонное «снести всё tick-scoped» несовместимо с assert-only.
Замена: запрос несёт `as_of: Option<u64>`; `Ticked`-предикат под `as_of = t` отдаёт ассершны с
`tick == t`, под `as_of = None` — ассершны с максимальным тиком. Стор ничего не удаляет; забывание
делает горизонт-компакция (§6.5 M3), и она — политика хранения, а не семантика.

Способность `as_of_tick` объявляется в `Capabilities` (§7.3), и план, требующий её от бэкенда,
который её не несёт, отклоняется `E-CAP-001`, а не деградирует молча.

противоположное: абортит ДО коммита кодами `E-MAT-002/009/010` (`derive/materialize.rs:48-52`,
`:309-322`), `E-PLAN-003` (`derive/plan.rs:160-167`, гейт `MAX_MATERIALIZED_FACTS = 10_000_000`
`plan.rs:42-43`), `E-EXEC-001/002/003` (`derive/exec.rs:132-142`), плюс wall-clock дедлайн 30 s
(`datalog/eval.rs:218-229`).

**Из одного и того же входа получаются РАЗНЫЕ базы.** Это не деталь — это политика, и она
не решается документом. §11 O-4 (открытый вопрос, владелец).

Что документ фиксирует независимо от решения:

1. `hole/2` входит в нормативный список рефлексивных предикатов (§2.7) в ЛЮБОМ случае — даже при
   политике «аборт», потому что дырка нужна для `why-not` (`derive/exec.rs:267` `GapWitness`,
   `graph/engine_v2.rs:820` `explain_datalog_fact`).
2. **Идентичность дырки обязана быть контент-производной.** В v0 это процесс-локальный счётчик
   (`api.ts:22-23`, `:194` `$q(this.qn)`), поэтому два процесса, задавшие одни и те же запросы в
   разном ПОРЯДКЕ, получают разное каноническое состояние. Для долгоживущего мультиклиентного RFDB
   это неприемлемо: `QueryId = BLAKE3(canon(query_term, perspective))`.
3. Частичный коммит, если он будет выбран, ОБЯЗАН быть атомарным вместе со своей дыркой: `hole`-факт
   и частичные факты — один `CommitToken`. Иначе база может нести частичный результат без отметки
   о частичности — режим отказа хуже обоих вариантов.

## 3. Физические стратегии per-predicate

### 3.0. Сначала — обрушение предпосылки

Пункт (5) брифа гласит: «бинарные предикаты над `Id × Id` сохраняют СЕГОДНЯШНЮЮ раскладку
смежности (edge segments + keyed indexes) … ничто на горячем пути не становится медленнее».
Обоснованием служили доккомменты `derive/storage_glue.rs:327-353`.

**Эта предпосылка ложна, и это проверено чтением кода на HEAD.**

| Утверждение доккомментов | Реальность |
|---|---|
| `edges_from` (`storage_glue.rs:332`) — «Backed by storage's keyed source index (snapshot-pinned), NOT a full relation scan — the access cost is proportional to `src`'s fan-out» (`:327-328`) | `get_outgoing_edges_at` (`storage_v2/multi_shard.rs:1139-1180`): `if !seg.maybe_contains_src(node_id) { return; } for j in 0..seg.record_count() { if seg.get_src(j) != node_id { continue; } … }` — **bloom-гейт + линейный скан каждой записи каждого сегмента-кандидата** |
| `edges_to` (`:339`) — «keyed destination index» (`:336`) | `get_incoming_edges_at` (`multi_shard.rs:1224+`): та же форма |
| `get_node` (`:343`) — «Bound-id point lookup» (`:341`) | `get_node_at` (`multi_shard.rs:852-895`): bloom + линейный скан, **включая L1**, хотя L1 после компакции отсортирован по `id` |
| `nodes_by_attr` (`:354`) — «snapshot-pinned attr index … not a full scan» (`:351-353`) | `find_node_ids_by_attr_chunked_at` (`multi_shard.rs:1492+`): полный скан сегментов с прунингом только по zone-map дескриптора |
| `base_estimate` (`derive/plan.rs:1114-1120`) — «storage_v2 serves a per-type edge index (`get_edges_by_type_at`), so `edge(_, _, "T")` is a keyed scan of one type's edges, not a full relation scan» | `get_edges_by_type_at` (`multi_shard.rs:1353-1392`): прунинг по `desc.edge_types` (zone map) + `seg.contains_edge_type` + **`for j in 0..seg.record_count()` с `if et != edge_type { continue; }`** — линейный скан внутри каждого непрунутого сегмента. Индекса нет |

Четвёртая строка — не косметика: **на этом доккомментарии стоит модель стоимости планировщика**.

Подтверждение отсутствия поиска: `grep -rn "binary_search" packages/rfdb-server/src/storage_v2/`
даёт ровно два хита — `index/global.rs:57` и `index/query.rs:71` (оба вне снапшот-пути);
`grep -rn "partition_point" storage_v2/` — пусто. Это независимо подтверждено сиблинг-документом
`_ai/research/rfdb-datalog-storageview-contract.md` («Gaps» п.1).

**Переформулировка пункта (5), нормативная:** сохранять надо не «keyed adjacency layout» (его нет),
а **колоночный декод + bloom-прунинг + zone-map прунинг**. И одновременно: сортировка на L1 уже
есть (`compaction/merge.rs:43-44` узлы по `id`, `:63-66` рёбра по `(src,dst,edge_type)`) — она
просто **не используется на чтении**. Бинарный поиск по L1 — это бесплатный выигрыш, не зависящий
от ROFL, и он вынесен в фазу P1 (§10.4) именно поэтому.

### 3.1. Каталог предикатов

Стратегия не выводится и не угадывается — она **объявляется** и персистится.

```rust
pub struct PredicateDecl {
    pub id:          PredicateId,   // u32
    pub name:        String,        // "CALLS", "name", "line", "span", "supersedes"
    pub arity:       u8,            // единственный арность-контракт; заменяет E-MAT-002/009
    pub strategy:    PhysStrategy,
    pub cardinality: Cardinality,   // §2.3 — Functional | MultiValued
    pub temporal:    TemporalScope, // §2.8 — Timeless | Ticked
    pub semiring:    u16,           // BOOLTAG_SEMIRING_ID по умолчанию
    pub key_cols:    Box<[u8]>,     // индексы колонок, образующих ключ сортировки
    pub reverse:     Option<Box<[u8]>>,  // §6.3 — сорт-ключ обратного рана, если он объявлен
    pub author_priority: Box<[AuthorId]>, // §2.3, шаг 1 разрешения конфликта
    pub stats:       PredicateStats, // §3.4 — НЕ опционально
}

/// Статистика, на которой стоит планировщик. Персистится в манифесте,
/// обновляется компакцией (она и так проходит по всем строкам предиката).
pub struct PredicateStats {
    pub live_facts:    u64,          // точное число живых фактов
    pub live_asserts:  u64,          // точное число живых ассершнов
    pub distinct:      Box<[u64]>,   // на колонку: число различных значений
    pub max_fanout:    u64,          // max |{строк с данным key_cols[0]}|
    pub updated_at_tx: u64,          // версия манифеста, на которой посчитано
}
```

Каталог живёт в манифесте (рядом с `SegmentDescriptor`, `manifest.rs:394-424`), версионируется
вместе с ним, и является **единственным местом**, где предикат получает физику. Смена стратегии
предиката — это запись в каталог + перекомпакция этого предиката, а не миграция базы.

| Стратегия | Форма кортежа | Сорт-ключ | Что наследует из сегодняшнего кода |
|---|---|---|---|
| `Adjacency` | `(Id, Id)` | `(c0, c1)` и `(c1, c0)` — два рана | edge-сегменты, bloom по src и dst (`writer.rs:373-434`), zone-map по предикату вместо `edge_type` |
| `Attribute` | `(Id, Scalar)` | `(c0)` прямой, `(c1, c0)` обратный | node-сегменты, string table, bloom по `c0` |
| `Composite` | `(Id, S1..Sk)`, k ≤ 8 | `(c0)` | node-сегменты; **новое**: n-арный кортеж в одной строке |
| `Nary` | произвольная | `(c0)` по умолчанию | **новое целиком** — дефолт для открытого пространства |
| `Reified` | `(Fid, ...)` | `(c0)` | `Adjacency` с `c0 = fid`, а не `entity id` |

Предикат без объявления получает `Nary` / `MultiValued` / `Timeless` / без обратного рана.
Это гарантирует, что **открытость пространства предикатов (пункт 4 брифа) не требует ничьего
разрешения**: новый вид сущности — это новый предикат, а не новая type-СТРОКА внутри фиксированной
записи. Но статистика по нему всё равно набирается компакцией, поэтому планировщик не слепнет
(§3.4).

**Блокер `tag_fold`, нормативное решение.** `compaction/tag_fold.rs:36-63` сегодня сворачивает теги
дублирующихся записей ⊕-операцией семиринга — потому что «дубликат» в записевой модели означает
«та же сущность, переписанная позже». В фактовой модели это неверно: две строки с одним `fid` — это
**разные ассершны разных авторов**, и свёртка их тегов в один уничтожает `supportCount` (§2.1),
делает `asserted_by` многозначным-но-несчитаемым и ломает §9.1, который хеширует ассершны поимённо.

> **Нормативно: ключ свёртки `tag_fold` — `aid`, то есть `(fid, author, tick)`, а не `fid`.**
> ⊕ применяется ТОЛЬКО внутри одного `aid` (один автор, один тик — то есть настоящий дубликат,
> порождённый повторной записью того же ассершна). Между разными `aid` теги НЕ сворачиваются
> никогда. `E-FMT-002` при разных `semiring_id` остаётся.

Второй, независимый дефект того же модуля: `CountTag` использует насыщающую арифметику
(`derive/tag.rs:169` `saturating_mul`, `:173` `saturating_add`, `:180` `saturating_sub`). Насыщение —
это молчаливо неверный ответ, и оно нарушает законы полукольца, на которых стоит гейт §9. Нормативно:
проверяемая арифметика, переполнение → **`E-TAG-001`**, аборт до коммита.

Третий: DRed-удаление (`derive/increment.rs`) выражает «отмену» через `InvertibleTag::minus`
(`tag.rs:177-182`). В фактовой модели отмена — это supersession ОДНОГО поддерживающего ассершна,
а не вычитание из агрегата. `minus` остаётся операцией семиринга для инкрементального пересчёта
`Count`, но **не является механизмом удаления** и не имеет права ставить `tx_invalidated`.

### 3.3. Стратегия покрывающего индекса (covering index) для узла

Запись узла выживает **как вид**, а не как истина. И это не новая конструкция: сегодняшняя v1-запись,
которую потребляет всё выше стора, уже синтетическая и уже частично фиктивная —
`node_v2_to_v1` (`graph/engine_v2.rs:30-51`) изобретает пять полей из двенадцати:
`file_id: 0` (`:37`), `name_offset: 0` (`:38`), `version: "main"` (`:39`), `replaces: None` (`:41`),
`deleted: false` (`:42`), а `exported` вообще не колонка — он извлекается из JSON-блоба по ключу
`__exported` (`:53-71`) и впрыскивается обратно на записи (`:74-91`). Обратное направление
хардкодит `content_hash: 0` (`:115`).

**Нормативно:** `NodeView` — это материализованный `Composite`-предикат
`node_view(E, node_type, name, file, exported)`, поддерживаемый инкрементально из ассершнов по
`node_type/1`, `name/1`, `file/1`, `exported/1` в перспективе запроса. **Он определён только потому,
что все четыре предиката объявлены `Functional` (§2.3)** — без этого «поле вида» не имело бы
однозначного значения. Он **не является истиной** и не участвует в каноническом хеше (§9).

Его единственный смысл — держать `http_server.rs:439/:800/:1526/:2186` (четыре полнографовых скана
`find_by_attr(&AttrQuery::default())`) на том же порядке стоимости: комментарий `http_server.rs:801-803`
фиксирует, что уже сегодня «333k get_node lookups is the dominant cold-start cost», и это потребовало
rayon.

**Честно: это самый рискованный по производительности потребитель всей миграции.** Без
covering-индекса он превращается в 5-путевое слияние поверх ~4.4M ассершнов узлов вместо 333k декодов
записи. Covering-индекс это чинит, но добавляет к записи стоимость поддержки вида. Цена не измерена
(U-1, §11 O-9).

### 3.4. Планировщик и исполнитель: с закрытого списка — на статистику (НОВОЕ в rev 2.0)

rev 1.0 не сказала об этом ни слова, и ревью назвало это блокером справедливо: **открытое
пространство предикатов несовместимо с сегодняшним движком вывода не по духу, а по букве.**

**Дефект 1 — планировщик знает пять имён.**

```rust
// derive/plan.rs:927
const BASE_RELATIONS: &[&str] = &["node", "type", "edge", "incoming", "attr"];
```

`base_estimate(rel, atom, pattern, stats)` (`plan.rs:1084`) — это `match rel { "node" | "type" => …,
"edge" | "incoming" => …, … }` с рукописной формулой на каждое имя. Оракул кардинальности
(`derive/builtin.rs:264-275`) несёт ровно три числа: `total_nodes`, `total_edges`, `nodes_by_type`.
**Пер-предикатной кардинальности в нём нет.** Открыв пространство предикатов, мы получаем 141
отношение (MEASURED, §6.2), из которых планировщик знает точную мощность нуля. Любой такой лег он
оценит в `total_nodes`/`total_edges` — то есть либо выберет катастрофический порядок джоинов, либо
споткнётся о гейт `MAX_MATERIALIZED_FACTS = 10_000_000` (`plan.rs:42-43`) и выдаст `E-PLAN-003`
(`plan.rs:160-167`) на корректной программе.

**Нормативно:**
1. `PredicateStats` (§3.1) — обязательная часть каталога, персистится в манифесте, обновляется
   компакцией (она уже проходит по всем строкам предиката — маргинальная стоимость нулевая).
2. `base_estimate` перестаёт быть `match` по имени и становится функцией от
   `(PredicateDecl, pattern)`: `live_facts` при свободных колонках, `live_facts / distinct[i]` при
   связанной колонке `i`, `max_fanout` как потолок зонда. Существующие пять формул становятся
   частными случаями и удаляются как спецкод.
3. `FactShape`/`FactStats` (`plan.rs:51-140`) — точные мощности предикатов, определённых **целиком
   ground-фактами** — уже реализуют ровно эту идею для программных таблиц. Обобщение = снять условие
   «целиком ground» и брать те же числа из каталога. **Механизм есть; расширяется его область.**

**Дефект 2 — `build-once` диспетчеризуется по строковому имени.**


Всё, что не в этом списке, падает в generic per-row eval (`exec.rs:2027+`), стоимость которого
измерена и записана в самом коде: **~240 µs на зонд** (`exec.rs:2615-2617`: *«~240µs/probe measured

136 из них по определению попадают на медленный путь. Плюс `builtin::lookup` (`exec.rs:1912-1919`)
для незарегистрированного имени **возвращает пустое отношение для позитивного лега и пропускает все
строки для негативного** — то есть незарегистрированный предикат даёт МОЛЧАЛИВО НЕВЕРНЫЙ ответ,
а не ошибку.

**Нормативно:**
1. Один обобщённый `build-once`, ключёванный не именем, а
   `(PredicateId, SortOrder, bound_column_mask)`. Четыре сегодняшние реализации — четыре частных
   случая одной формы «построй хеш-карту из одного отсортированного рана, зондируй O(1) на строку».
2. Незарегистрированный в каталоге предикат в программе — **`E-CAT-002`, аборт**, а не пустое
   отношение. Молчаливо-неверный ответ `exec.rs:1912-1919` устраняется как класс.
3. **Гейт последовательности (обязателен):** обобщённый `build-once` и статистический
   `base_estimate` реализуются и бенчмаркаются на СЕГОДНЯШНИХ пяти отношениях **до** фазы P4, против
   зафиксированного базлайна пак-фазы **56.2 s тёплая / ~74 s холодная** (`_ai/research/RESUME.md:30`,
   `_ai/research/resolve-datalog2-migration-synthesis.md:433,452,517`). Регрессия сверх этого
   базлайна блокирует P4. Обоснование: это единственный способ отделить «замедлил обобщённый джоин»
   от «замедлила фактовая раскладка» — после P4 их уже не разделить.

**Дефект 3 (наследованный) — `datalog/eval.rs` не переживает открытие пространства.**
Пять ветвей `reverse_attr_lookup` (`:1561-1589`), три из них O(n) по всему множеству узлов,
плюс wall-clock дедлайн 30 s (`:218-229`). Вся эта диспетчеризация **удаляется**: обратный ран
предиката (§6.3) делает `attr(FreeId, "key", "val")` префиксным зондом. Это не оптимизация, это
условие жизнеспособности.

### 4.2. Единственный настоящий семантический разрыв: арбитраж владения

`owned_node_surface_changed` (`graph/engine_v2.rs:181-192`) — **единственный реальный in-place
мутатор узла во всей системе** (обработчик `UpdateNodeVersion` — задокументированный no-op,
`bin/rfdb_server.rs:1841-1845`, тест `:6723`). Он сравнивает записи целиком и гейтится на совпадении
`materialized_source`. Задокументированная гарантия (`:1264-1276`): *«A FOREIGN producer's node at
the same id is still never rewritten (it keeps its own name/file/metadata)»*.

**У этой фразы нет перевода в модель, где `name`, `file` и `metadata` — три независимо авторских
ассершна.** Пер-атрибутное авторство ровно и делает «эта запись принадлежит производителю P»
бессмысленным.

**Нормативная замена:** supersession, скопированный по автору. Производитель `P`, публикуя факт
`f`, помечает supersede-нутыми **только свои** предыдущие ассершны над тем же `fid` и над
конфликтующими `fid` в объявленной им области. Чужие ассершны не трогаются никогда — они остаются
живыми ассершнами того же или другого факта.

**Что происходит дальше — и почему §2.3 обязателен именно здесь.** После такого supersession два
производителя могут оставить два ЖИВЫХ конфликтующих ассершна функционального предиката — ровно
измеренные 39 случаев. Сегодня «побеждает» тот, чью запись первой вернёт `get_node_at`. После
миграции побеждает объявленный приоритет автора, а проигравший становится **запрашиваемым фактом**
`conflict/5`. Это строго выразительнее сегодняшнего поведения, но это **изменение наблюдаемого
поведения в мульти-производительных сценариях** (K-3), и его надо подтвердить, а не портировать
механически.

Внутри разрыва спрятан выигрыш: O(N)-цикл владения `:1297-1318` (JSON-парсинг блоба каждого
кандидата ради чтения `_source`) становится индексированным зондом, как только `author` — колонка
первого класса.

## 5. Ключ, шардирование, tombstones

### 5.1. Проблема: `file` — ключ ТРЁХ независимых механизмов

Маршрутизация записи сегодня берёт ровно один вход — родительскую директорию пути файла:

```rust
// storage_v2/shard_planner.rs:43-51
pub fn compute_shard_id(&self, file_path: &str) -> u16 {
    let dir = Path::new(file_path).parent().and_then(|p| p.to_str()).unwrap_or("");
    let hash = blake3::hash(dir.as_bytes());
    let hash_u64 = u64::from_le_bytes(hash.as_bytes()[0..8].try_into().unwrap());
    (hash_u64 % self.shard_count as u64) as u16
}
```

Её собственный доккомментарий (`shard_planner.rs:40-42`) признаёт схлопывание: *«Files without a
parent directory (e.g., "file.js") hash the empty string, so they all land in the same shard»*.

| Механизм | Ключ | Файл |
|---|---|---|
| Маршрутизация шарда | `file` | `shard_planner.rs:43-51` |
| Область ретракции | `changed_files` | `multi_shard.rs:2156-2258` (`commit_batch_ext` массово tombstone-ит всё в изменённых файлах) |
| MVCC write-write конфликты | `file` | `multi_shard.rs:143` `file_last_committed_version: Mutex<HashMap<String,u64>>` |

Факт без файла — а это КАЖДЫЙ факт открытого предикатного пространства, не описывающий позицию в
исходнике, — проваливается во всех трёх: попадает в один и тот же шард (MEASURED вербатимной
переимплементацией: `file="" → shard 3 из 4, 7 из 8, 15 из 16`), никогда не попадает в
`changed_files` и потому **нератрактируем**, и не имеет ключа конфликта, то есть при конкурентных
писателях **молча last-write-wins**.

Плюс уже существующий перекос: MEASURED на реальной 16-шардовой 543 MB базе — узлы 6 565…77 214
на шард (11.8x max/min), рёбра 11 763…153 406 (13.0x).

Плюс: рёбра, чей `src` неизвестен в `node_to_shard` (`multi_shard.rs:110`), **молча выбрасываются** —
`multi_shard.rs:512-529` увеличивает `skipped` и не пишет ничего; зеркально `:2769-2783`.

### 5.2. Нормативное решение: маршрутизация по субъекту

**`route(fact) = blake3_u64(subject_id(fact)) % shard_count`**, где `subject_id` — значение колонки
`key_cols[0]` из каталога (§3.1), приведённое к u128; для не-`Id` первой колонки —
`blake3(canon(value))`. Переопределение на предикат допускается через `PredicateDecl`.

| Свойство | Сегодня (`file`) | После (`subject`) |
|---|---|---|
| Баланс | MEASURED 11.8x / 13.0x перекос | равномерный по построению (BLAKE3 uniform) |
| Fileless-факт | один шард, hotspot | маршрутизируется как любой другой; **hotspot исчезает по построению** |
| Локальность фактов сущности | нет понятия | **все факты о `E` в одном шарде** — ровно то, что нужно covering-индексу (§3.3) |
| Локальность файла | реанализ 1 файла = 1 шард | **реанализ 1 файла = веерная запись во все N шардов** ← РЕГРЕССИЯ |
| Ратракция | по файлу | по автору+области (§5.5) |
| Конфликты MVCC | по `file` | по `(perspective, predicate, subject)` |

Регрессия по локальности файла названа честно и не замазывается. Смягчение: путь записи уже группирует
батч по шардам перед записью, так что это N частичных сегментов вместо одного, а не N полных проходов;
но **это не измерено** (U-2, §11 O-8). Обоснование, почему регрессия принимается: главный потребитель
файловой локальности — delete-by-file — исчезает вместе с удалением (§5.5).

**Цена перехода — полная, и её надо назвать заранее:** `shard_count` фиксируется при создании базы
(`multi_shard.rs:49-72`, читается из `db_config.json`), кода решардинга в дереве нет вовсе, а
`clear_durable` (`graph/engine_v2.rs:1406-1442`) **сохраняет `db_config.json`** и перечитывает
`shard_count` из `self.cached_profile`. Значит смена функции маршрутизации — это не конфиг, не
rollout и **не `--clear`**: это **полная пересборка + переингест в НОВУЮ директорию базы**. Это
фаза P6 (§10.4), и раньше неё маршрутизацию трогать нельзя.

### 5.3. Идентичность: три несогласованных пути формирования id

`id = BLAKE3(semantic_id)` — это **соглашение, а не инвариант**:

| Путь | Код | Что делает |
|---|---|---|
| канонический | `graph/id_gen.rs:16-21` | `string_id_to_u128` = BLAKE3 первые 16 B LE |
| второй, структурно иной | `graph/id_gen.rs` | `compute_node_id(node_type, name, scope, path)` |
| wire-резолвер | `bin/rfdb_server.rs:1007-1013` | `string_to_id`: **сначала пытается распарсить как десятичное число**, и только потом хеширует |
| мост v1→v2 | `graph/engine_v2.rs:101-124` | ставит `id: v1.id` и **синтезирует** `semantic_id` после, так что `BLAKE3(sid) != id` практически всегда |

Опасность задокументирована самим кодом — `E-MAT-010` (`derive/materialize.rs:309-322`): *«the node
writer derives the id as BLAKE3(sid) while the wire resolver parses a decimal sid as the id directly,
so such a node would be unreachable by sid»*. Рантайм-проверки инварианта нет нигде.

**Нормативно:** `fid = BLAKE3(canon(...))[0..16] LE` проверяется на границе стора кодом `E-KEY-001`.
Десятичный парс из `string_to_id` **удаляется** — строка всегда хешируется. Это ломает клиентов,
передававших числовой `semantic_id` (объём UNVERIFIED, §11 O-5).

Побочное требование: `fid` **обязан оставаться равномерным**, потому что `bloom.rs:31-46` не хеширует
ключ вовсе (*«The u128 key (already a BLAKE3 hash) is split into two 64-bit halves»*). Структурный
композитный ключ вместо хеша **молча** испортил бы FPR. Поэтому §2.2 фиксирует именно BLAKE3, а не
конкатенацию полей.

### 5.4a. Perspective на ЧТЕНИИ: неинтерференция по построению

**Исправление rev 1.0 (блокер ревью).** rev 1.0 объявляла перспективу компонентом ключа и на этом
останавливалась. Ревью справедливо указало: если перспектива — не обязательный параметр КАЖДОГО
примитива чтения, то первая же забытая передача даёт молчаливую утечку фактов между перспективами,
и никакой тест этого не поймает, потому что на сегодняшней базе перспектива одна.

**Нормативно, три уровня защиты:**

1. **Тип.** Ни один метод трейта `FactStore` (§7.2) не читает без `perspective`. `Snapshot` НЕ несёт
   перспективу — она параметр вызова, потому что один запрос законно читает несколько перспектив
   (`audit` + рабочая).
2. **Раскладка.** `perspective` — старший компонент сорт-ключа ВСЕГДА, для любой стратегии
   (§3.1). Следствие: срез по перспективе — префиксный ран, а не фильтр. Пропустить фильтрацию
   физически нельзя: без префикса нет входа в ран.
3. **CI-гейт.** Грепом: ни один вызов `sorted_run`/`prefix_scan`/`get_fact` вне крейта
   `rfdb-facts` не имеет права конструировать `PerspectiveId` литералом или дефолтом. Проверяется
   так же, как правило 2 из §8 — механическим тестом, а не декларацией.

Матчинг — **точное равенство**, как в v0. Обоснование не эстетическое: v0 не консультируется с
преордером видимости нигде (`grep -n "sees\|imports\b" src/*.ts` → ноль хитов; `README:130-133`
дословно: *«Visibility enforcement is exact-perspective matching … `imports`/`sees` are audit-level
data (boot's `leak`), not kernel matching rules»*; `LIMITS.md:44-45`: *«Queries are god-view»*).
Если RFDB начнёт форсить видимость в планировщике, он **выведет МЕНЬШЕ фактов, чем v0**, а
`leak[audit]` из `boot.rofl:30-31` станет вакуумным — молчаливая семантическая вилка с оракулом.

### 5.4b. Perspective на ЗАПИСИ: мост объявляется, а не случается

Чтение точным равенством не даёт неинтерференции само по себе: правило, читающее из `P1` и пишущее
в `P2`, переносит факты между перспективами законно и незаметно. В v0 это разрешено декларацией —
`bridge_decl` (`/tmp/rofl-v0/src/api.ts:136-139`).

**Нормативно:**

1. Правило объявляет перспективу головы. По умолчанию она совпадает с перспективой тела.
2. Правило, тело которого читает `P_read`, а голова пишет `P_write ≠ P_read`, ОБЯЗАНО нести
   объявление `bridge_decl(RuleId, P_read, P_write)` — **факт**, а не атрибут синтаксиса (§2.7).
3. Мост без объявления — **`E-PERSP-001`**, аборт до коммита.
4. Мосты запрашиваемы: `bridge_decl` — обычный предикат, поэтому «какие перспективы связаны и кем»
   отвечается запросом, а не чтением исходников правил. Это то самое свойство, ради которого
   `boot.rofl` вообще существует.

### 5.5. Tombstones → supersession: что именно уходит

| Сегодня | Evidence | После |
|---|---|---|
| `TombstoneSet { node_ids: HashSet<u128>, edge_keys: HashSet<(u128,u128,Arc<str>)> }` | `shard.rs:78-153` | **удаляется** |
| Кумулятивные списки в JSON-манифесте: `tombstoned_node_ids: Vec<u128>`, `tombstoned_edge_keys: Vec<(u128,u128,String)>` | `manifest.rs:186-212` | **удаляется** — это монотонно растущий JSON-массив, чистящийся только `CompactionTier::FullMerge` |
| Массовый tombstone всего в `changed_files` | `multi_shard.rs:2156-2258` | → «supersede все ассершны, чей `author` = этот производитель И чья область пересекается с объявленной» |
| Асимметричное удаление рёбер (только исходящие; входящие остаются висеть и фильтруются по tombstone на чтении) | `bin/rfdb_server.rs:2417-2430` | **удаляется целиком** — висячих ссылок нет по построению |
| Молчаливый дроп ребра с неизвестным `src` | `multi_shard.rs:512-529`, `:2769-2783` | **удаляется** — факт с неизвестным `Id` в аргументе корректен; неограниченная молчаливая потеря данных прекращается |

Область ретракции объявляется явно, а не выводится из поля данных:

```rust
pub struct SupersedeScope {
    pub author:      AuthorId,
    pub perspective: PerspectiveId,
    pub predicate:   Option<PredicateId>,   // None = все предикаты автора
    pub subject_set: SubjectSet,            // Explicit(Vec<u128>) | ByAttr{pred, values} | All
}
```

`ByAttr { pred: file, values: changedFiles }` воспроизводит сегодняшний контракт реанализа **точно**,
но теперь это явный аргумент, а не побочный эффект поля `node.file`. Отсюда прямо следует критерий
**C2**: шесть энричеров возвращаются на `BatchHandle.commit()`, потому что батч без `SupersedeScope`
аддитивен по определению.

### 5.6. Долговечность и crash-consistency (НОВОЕ в rev 2.0)

**Исправление rev 1.0 (блокер ревью).** rev 1.0 писала «tombstone-списки удаляются» и не сказала,
чем заменяется механизм, который эти списки делает КРАШ-БЕЗОПАСНЫМИ. Это не деталь: две
data-loss-регрессии RFD-74 жили ровно здесь и были отгружены в опубликованной 0.4.0
(`packages/rfdb-server/src/storage_v2/manifest.rs:2744`, `:2820`).

Сегодняшний механизм и его инвариант:

```rust
// storage_v2/manifest.rs:1590-1605  (доккомментарий :1594-1595)
/// Invariant: replaying the edit chain since the last checkpoint reproduces
/// the snapshot a full-write commit would have produced.
pub fn commit_edit(
    &mut self,
    mut edit: ManifestEdit,
    checkpoint_tombstone_nodes: &[u128],
    checkpoint_tombstone_edges: &[(u128, u128, String)],
) -> Result<()>
```

То есть: между чекпойнтами персистится ДЕЛЬТА tombstone'ов, на чекпойнте — полное кумулятивное
множество; корректность = «реплей цепочки правок с последнего чекпойнта воспроизводит снапшот».

**Нормативно: механизм СОХРАНЯЕТСЯ целиком, меняется только его содержимое.**

| Компонент | Сегодня | После |
|---|---|---|
| Дельта между чекпойнтами | `tombstone_delta` | **`supersede_delta: Vec<(aid, tick)>`** — ассершны, ставшие мёртвыми в этой версии |
| Полный набор на чекпойнте | кумулятивный tombstone-set | **не нужен**: `supersedes`-факты уже лежат в сегментах как обычные факты; чекпойнт материализует их в `tx_invalidated`-кэш |
| Инвариант реплея | как в доккомментарии | **дословно тот же**, с заменой «tombstone» на «supersede» |
| Рост | кумулятивный JSON-массив, чистится только `FullMerge` | ограничен интервалом между чекпойнтами (дельта не кумулятивна) |

Ключевое улучшение по существу: сегодня «что удалено» существует ТОЛЬКО в манифесте, поэтому потеря
манифеста = потеря удалений (это и был класс RFD-74). После миграции «что superseded» — это факты в
сегментах; манифест несёт лишь **кэш** (§2.4). Потеря дельты манифеста означает потерю
оптимизации, а не потерю истины.

**Обязательный гейт последовательности:** тестовый файл `packages/rfdb-server/tests/crash_recovery.rs`
переносится на фактовую модель и должен быть ЗЕЛЁНЫМ **до** удаления tombstone-списков (фаза P7).
Он несёт девять тестов, из которых пять покрывают ровно этот путь: `commit_batch_tombstones_work_within_session`
(`:182`), `commit_batch_tombstones_survive_restart` (`:216`), `flush_tombstone_persists_after_reopen`
(`:256`), `incremental_flushes_accumulate` (`:299`), `delete_then_readd_persists_correctly` (`:328`).
Плюс обе mutation-proven crash-injection регрессии RFD-74.

**Оговорка честности (UNVERIFIED-риск процесса):** `grep -c cargo .github/workflows/ci.yml` → **0**.
Ни один CI-воркфлоу в этом дереве не запускает `cargo test`. Значит гейт P7 не может опираться на
«CI зелёный» — он обязан быть явным ручным/скриптовым прогоном в чеклисте фазы, иначе он не гейт.

### 6.4. Горизонт тиков — и место, где план может умереть

    S(H) = D + S_fact × (1 + χ·H)                 [равномерный churn]
    S(H) = D + S_fact × (1 + Σ_{i=1..H} χ_i)      [измеренный по-тиковый churn]

Вариант A+R: `D = 101 849 805 B` (97.1 MiB словарь термов, не растёт),
`S_fact = 382 812 279 + 200 590 656 = 583 402 935 B`, `S0 = 685 252 740 B (653.5 MiB)`.

MEASURED χ на этой базе (диф множеств сегментов по 28 удержанным версиям манифеста):
**медиана 0.03%, среднее 4.60%, максимум 92.34%** (компакция L1, переписавшая все 16 шардов).

в неубранных осиротевших сегментах (260.9 MiB против 217.2 MiB) и имеет 2.14x кумулятивной

**Побочное следствие для §7.4.** Глобальный L1-индекс — `IndexEntry` ровно 32 B

**2.29 GiB резидентно на один индекс**. Это самостоятельный аргумент за то, что глобальный индекс
в фактовой модели обязан стать пер-предикатным и дисковым, а не глобальным и резидентным.

### 6.5. Смягчение, в порядке убывания рычага

| # | Механизм | Эффект | Статус |
|---|---|---|---|
| **M1** | **Дедуп по переутверждению.** Повторное утверждение того же `(fid, author, tag)` — **NO-OP на границе стора**, не новый ассершн. Это обобщение уже существующей семантики: `WriteBuffer` держит `nodes: HashMap<u128, NodeRecordV2>` с upsert и `edge_keys: HashSet<(u128,u128,String)>` (`write_buffer.rs:36-50`), то есть дедуп внутри батча УЖЕ есть — расширяется до дедупа между тиками через живой ассершн | Переводит режим χ=1.0 в режим χ≈0.0003 для НЕИЗМЕНИВШЕЙСЯ части графа. **Единственное смягчение, меняющее порядок величины** | новое; опирается на существующий механизм |
| M1-alt | Оживить `content_hash` (MEASURED мёртв: 0/503 443) | То же по эффекту, но требует изменений в ДРУГИХ пакетах (производители узлов), а не только в RFDB | **вынесено из пререквизитов P7** — см. ниже |

| M6 | A″ span-коллапс | −24% по счёту фактов (MEASURED) | требует решения K-5 / §11 O-2 |

**Исправление rev 1.0 (блокер ревью): M1 больше не «оживить `content_hash`».** rev 1.0 объявляла
живой `content_hash` **пререквизитом фазы P7**. Это неверно по области ответственности: `content_hash`
пишут ПРОИЗВОДИТЕЛИ узлов (анализаторы, оркестратор, энричеры — другие пакеты), RFDB его только
хранит, на проводе его нет вовсе (`bin/rfdb_server.rs:846-866`), и его единственный потребитель
гейтится на ненулевом значении с обеих сторон. Ставить кросс-пакетную работу пререквизитом
внутри-RFDB фазы — значит гарантированно заблокировать P7.

**Нормативно:** пререквизит P7 — **M1 (дедуп по переутверждению)**, механизм целиком внутри стора.
`content_hash` (M1-alt) остаётся отдельной кросс-пакетной работой со своей фазой и своим владельцем;
он усиливает M1 (позволяет НЕ ГЕНЕРИРОВАТЬ факты вовсе, а не отбрасывать их на границе), но не
блокирует его. Риск K-4 назван: если дедуп не срабатывает — например, автор переутверждает с новым
`tag` или новым `tick` при неизменном содержании — режим χ=1.0 остаётся, и таблица §6.4 применяется
как есть.

**Измеренный драйвер χ=1.0, который дедуп НЕ ловит.** Оркестратор на каждом коммите layout пишет
метаданные с `committed_at: iso8601_utc_now()` (`layout/commit.rs:331`, `:443`) на ~35k размещаемых
узлов (`layout/loader.rs:31`). Это **волатильная колонка**: её значение меняется при неизменном
содержании, поэтому `(fid, author, tag)` каждый раз новый и дедуп бессилен. Нормативное правило:

> Волатильное значение (время коммита, случайный идентификатор запуска, счётчик) НЕ имеет права
> находиться в кортеже факта. Его место — колонка ассершна (`tick`) или отдельный факт о ЗАПУСКЕ
> (`run_committed_at(RunId, T)`), на который факты ссылаются по `RunId`.

Без этого правила один пакет-потребитель в одиночку удерживает всю базу в режиме χ=1.0.

## 7. Контракт стора отношений

### 7.1. Почему НЕ ordered-KV

Ordered-KV — это форма RocksDB. Заставить own-LSM (колоночные сегменты + манифест + zone-map + bloom)
реализовать ordered-KV — значит получить фальшивый адаптер, который потеряет свои преимущества и
сделает сравнение нечестным. Честный общий знаменатель, зафиксированный владельцем:
**«отсортированные раны над (perspective, predicate, tuple) с пер-предикатной физической стратегией»**.

Оговорка честности: **этого знаменателя не существует сегодня даже для графового случая.** Сегменты
пишутся НЕотсортированными (`write_buffer.rs:3` дословно: *«Analogous to LSM-tree memtable. NOT
sorted (L0 segments are unsorted)»*). Единственная сортировка в системе — в компакции, и её ключ
жёстко зашит (`compaction/merge.rs:43-44`, `:63-66`). Обобщённой абстракции сорт-ключа наследовать
не от чего.

### 7.2. Трейт

```rust
/// Стор ОТНОШЕНИЙ. Единица — предикат, а не ключ. Реализуется обоими бэкендами.
pub trait FactStore: Sync {
    // ── каталог ──────────────────────────────────────────────
    fn catalog(&self) -> &PredicateCatalog;
    fn declare(&mut self, decl: PredicateDecl) -> Result<PredicateId>;
    fn capabilities(&self) -> Capabilities;

    // ── чтение ───────────────────────────────────────────────
    // Снапшот НЕ несёт перспективу: она параметр каждого вызова (§5.4a).
    // Единица чтения — FactRow (кортеж + его живые ассершны), НЕ Assertion (§2.2).
    fn snapshot(&self) -> Snapshot;

    /// Отсортированный ран предиката в заданном порядке — путь merge-join.
    fn sorted_run<'a>(&'a self, s: &'a Snapshot, p: PredicateId, persp: PerspectiveId,
                      o: SortOrder) -> Box<dyn Iterator<Item = FactRow> + 'a>;

    /// Префиксный зонд: все факты предиката, чей сорт-ключ начинается с `prefix`.
    /// Обобщение edges_from/edges_to/get_node/nodes_by_attr в ОДИН примитив.
    fn prefix_scan<'a>(&'a self, s: &'a Snapshot, p: PredicateId, persp: PerspectiveId,
                       o: SortOrder, prefix: &[Value]) -> Box<dyn Iterator<Item = FactRow> + 'a>;

    /// Точечный зонд по fid. §8.3 остаётся в силе: запрещён в горячем цикле фикспойнта.
    fn get_fact(&self, s: &Snapshot, fid: u128) -> Option<FactRow>;

    /// Обратное отображение fid → кортеж. Нужно рефлексии (§2.7) и DerivationWitness,
    /// которым fid приходит как ЗНАЧЕНИЕ. BLAKE3 односторонний — без этого метода
    /// кортеж не восстановим.
    fn tuple(&self, s: &Snapshot, fid: u128) -> Option<Box<[Value]>>;

    /// Живость (§2.4): отфильтровать мёртвые ассершны anti-join'ом с `supersedes`.
    /// Явный примитив с НАЗВАННОЙ стоимостью, а не скрытая проверка колонки.
    fn live_filter<'a>(&'a self, s: &'a Snapshot, rows: Box<dyn Iterator<Item = FactRow> + 'a>)
        -> Box<dyn Iterator<Item = FactRow> + 'a>;

    /// Разрешение функционального конфликта (§2.3). Возвращает победителя и,
    /// если спор решался не приоритетом автора, порождённые факты conflict/5.
    fn resolve_functional(&self, s: &Snapshot, p: PredicateId, persp: PerspectiveId,
                          subject: u128) -> Option<(FactRow, Vec<FactKey>)>;

    // ── запись ───────────────────────────────────────────────
    fn assert_batch(&self, b: AssertBatch) -> Result<CommitToken>;
    fn supersede(&self, scope: SupersedeScope, at_tick: u64) -> Result<CommitToken>;
    fn begin_bulk_load(&mut self) -> Result<()>;
    fn end_bulk_load(&mut self) -> Result<()>;

    // ── обслуживание ─────────────────────────────────────────
    fn compact(&self, p: Option<PredicateId>, tier: CompactionTier) -> Result<()>;
    /// Статистика для планировщика (§3.4). Обновляется компакцией.
    fn stats(&self, p: PredicateId) -> &PredicateStats;
    /// C3: хеш ЛОГИЧЕСКОГО множества фактов, не байт. §9.
    fn canonical_state_sha(&self, s: &Snapshot) -> [u8; 32];
}
```

Четыре сегодняшних метода `edges_from` / `edges_to` / `get_node` / `nodes_by_attr`
(`derive/storage_glue.rs:332`, `:339`, `:343`, `:354`) схлопываются в `prefix_scan` над предикатом с
объявленным порядком. Это не потеря — это ровно то обобщение, которого не хватало: сегодня
`nodes_by_attr` обязан знать, какие имена привилегированы, а какие живут в блобе, и именно этот
раскол порождает пятиветочную диспетчеризацию `datalog/eval.rs:1561-1589`.

### 7.3. Переговоры о способностях

## 9. Канонический хеш состояния

Требуется критерием C3. **Сегодня не существует.**

### 9.1. Нормативное определение

`canonical_state_sha` хеширует **ЛОГИЧЕСКОЕ множество фактов**, а не физические байты. Иначе
компакция, флаш, смена `shard_count`, порядок сегментов и L0-затенение L1 (MEASURED: 39 дублей по
`id`, 71 по `semantic_id` — ровно этот эффект) меняли бы хеш при неизменной истине.

```
canonical_state_sha(S) = BLAKE3(
    "ROFL-STATE-v1\n"
  ⧺ varint(tick)
  ⧺ for each LIVE fact f in CANONICAL ORDER:
        canon_bytes(f.perspective, f.predicate, f.tuple)
      ⧺ varint(|live assertions of f|)
      ⧺ for each live assertion a of f, sorted by (author, tick):
            u32(author) ⧺ u64(tick) ⧺ u16(tag.semiring_id) ⧺ len-prefixed(tag.bytes)
)
```

**Живость определяется §2.4 (отсутствие живого `supersedes(_, aid)`), а НЕ значением
`tx_invalidated`.** Это исправление rev 1.0: там живость определялась через колонку-кэш, из-за чего
две логически идентичные базы с разной историей компакции давали разные хеши.

**Согласование с `tag_fold` (блокер ревью).** Хеш перечисляет ассершны поимённо, поэтому свёртка
тегов на компакции обязана быть тождественной относительно него. Отсюда и следует правило §3.2:
⊕ применяется только внутри одного `aid`. Гейт (часть C3): факт `Count`, утверждённый ДВУМЯ
авторами, обязан после `compact()` дать тот же `canonical_state_sha`, что до неё, и обязан сохранить
`|live assertions| == 2`. Это ровно тот случай, который сегодняшний `tag_fold` схлопнул бы в один.

### 9.2. Каноническая упорядоченность

| Позиция | Компонент | Правило |
|---|---|---|
| 1 | `perspective` | по канонической строке имени перспективы, побайтово по UTF-8 |
| 2 | `predicate` | по канонической строке имени предиката, побайтово по UTF-8 |
| 3 | `tuple` | лексикографически по `canon_bytes` кортежа; внутри — по вариантному тегу значения, затем по полезной нагрузке |

**Не по интернированным `u32`-идентификаторам** — они зависят от порядка объявления и от процесса.
Хеш обязан быть инвариантен к порядку объявлений, к числу шардов, к количеству и границам сегментов,
к тому, был ли факт записан в L0 или уже скомпакчен в L1.

Обязательные предпосылки, без которых хеш недетерминирован: `E-VAL-001` (`BigInt`, влезающий в `i64`,
обязан быть `Int(i64)`), `E-VAL-002` (`Float` канонизирован), плюс каноническое кодирование
`Value::Term` (§2.7) и контент-производный `QueryId` дырки (§2.9, п.2).

### 9.3. Ловушка коллации против v0 — назвать заранее

v0 канонизирует ключ в **СТРОКУ** (`store.ts:25-27`, `unify.ts:77-87`) и сортирует состояние
лексикографически по этим строкам (`store.ts:156-170`). Следствия: `"10" < "9"`; `mki(-3)` даёт `-3`
и сортируется раньше любой цифры.

**Критерий C4 («оба бэкенда дают идентичные результаты вычисления И идентичный canonical state sha»)
выполним между RocksDB и own-LSM, но МОЛЧА невыполним против v0** без отдельного режима
`--rofl-v0-collation`, воспроизводящего строковую коллацию v0. Нормативно: **C4 ограничена
сравнением бэкендов**; конформанс к v0 — отдельный критерий C5, и он **семантический** (множество
выведенных фактов), а не sha-побайтовый.

Вторая, независимая причина, почему sha-равенство с v0 невозможно: v0 указывает провенансом на
**реифицированную копию всего кортежа** (`src/reflect.ts:111-114` — `factTerm` строит
`$fact(rel, persp, list(args))`; `src/engine.ts:302-307` — `derived_by` эмитится с этим термом на
каждое новое срабатывание), и это измеренный драйвер стоимости: *«k=14 → 590,838 facts / 70.9s;
facts grow ~x2.1 per k; honest ceiling k≈16»* (`run/SUBSTRATE_ISSUES.md:41-49`), перепроверено
независимо на ×2.04 (§2.7). RFDB указывает провенансом на `fid`. **Выбирается одно: дешёвый
провенанс ИЛИ sha-равенство с v0. Документ выбирает дешёвый провенанс.**

Сноска о числе «71 s»: оно же стоит критерием в ТЗ
(`a03da7a6-rfdbroflspec.md:133`, A11 — *«Terras k=14 rebuild beats the TS baseline (71s) by ≥5×»*) и
относится к **Collatz/Terras-нагрузке** (`run/collatz-models.rofl`), а не к штатным примерам ядра:
на `tm.rofl` / `tm_diverge.rofl` прогон занимает 15–29 мс. Нагрузка живёт на ветке ⟨R⟩ и в
`main@052a4c5` отсутствует — это предусловие постановки A11 в CI (O-16).

Третья причина, техническая: идентичность дырки в v0 — процесс-локальный счётчик
(`api.ts:22-23`, `:194`), поэтому два процесса, задавшие одни и те же запросы в разном ПОРЯДКЕ,
получают разное каноническое состояние. §2.9 п.2 это чинит на стороне RFDB — ценой ещё одного
расхождения с v0.

### 9.4. Что означает `node_count` после миграции

`session.rs`, `static_ui.rs`, `metrics.rs`, `database_manager.rs` читают агрегаты. Под монотонным
ростом «сколько узлов» становится двусмысленным. Нормативно вводятся четыре различных числа, и
поверхность обязана сказать, какое она отдаёт:

| Метрика | Определение |
|---|---|
| `entities` | число живых фактов предиката `sid` в перспективе |
| `facts` | число живых фактов (§2.4) |
| `assertions` | число живых ассершнов (`facts` ≤ `assertions`) |
| `rows` | число физических строк, включая обратные раны и мёртвые ассершны — единственное, что коррелирует с байтами на диске (§6.3) |

## 10. Миграция

### 10.1. Можно ли конвертировать существующую базу на месте

Три поля ассершна (`author`, `tick`, `perspective`) обязаны появиться у каждого факта. Вопрос —
восстановимы ли они из того, что уже лежит на диске. Ответ измеряется, а не угадывается.

Оркестратор штампует в метаданные каждой записи два поля: `_generation` (счётчик прогона) и
`_source` (имя произведшего плагина) — `grafema-orchestrator/src/gc.rs:141-176`
(`stamp_node_metadata` / `stamp_edge_metadata` → общий `stamp_metadata`), счётчик живёт в
`GenerationTracker` (`gc.rs:49-137`) и персистится в `.grafema/gen-tracker.json`
(`grafema-orchestrator/src/main.rs:932`).

**MEASURED — покрытие на реальной базе** (копия `.grafema/graph.rfdb` в `/tmp/rofl-measure/`,
оригинал не трогался):

```

```

Синтаксически — почти всё. Но дальше начинается честная часть.

**MEASURED — разрешающая способность этих полей:**


Три вывода, каждый — ограничение:

1. **`tick` восстановим формально, но почти без информации.** 502 046 из 502 290 узлов
   (99.95% имеющих поле) несут `_generation = 1`; у рёбер 1 003 317 из 1 071 909 (93.60%). После

   различимости тиков), но означает: **`as_of`-запросы по конвертированной базе бесполезны**, и
   первый содержательный горизонт тиков появится только после первого пост-миграционного прогона.
   Числа §6.4 про χ и горизонт H применимы только к будущим прогонам, не к конвертированному
   прошлому.
2. **`author` восстановим и содержателен** (18 и 47 различных значений), но домен НЕ является
   контролируемым словарём: среди значений `_source` рёбер встречаются сырые sha256-хексы
   (`79fcbd36f43e…` — 37 754 ребра, `28b7cc18c180…` — 7 818). Конвертер обязан либо
   нормализовать их в объявленных авторов, либо занести как есть и **зарегистрировать это как
   загрязнение**, потому что порядок приоритета авторов (§2.3, разрешение `Functional`) опирается
   на объявленный список.
3. **`perspective` НЕ восстановима ничем.** В сегодняшней записи нет ни одного поля, из которого её
   можно вывести — ни `_source` (это автор, не перспектива), ни `file`, ни тип. Нормативно:
   **все конвертированные факты попадают в перспективу `main`**, и это записывается в манифест
   конверсии явным фактом, а не подразумевается. Всё, что относится к §5.4a/§5.4b (неинтерференция,
   мосты), начинает работать только для НОВЫХ фактов.

**Вердикт: конверсия на месте технически возможна для `author`/`tick` и невозможна для
`perspective`.** Записи без `_source`/`_generation` (917 узлов и 33 096 рёбер = 0.18% / 2.99%)
получают `author = $legacy`, `tick = 0`; конвертер обязан вывести их точное число в отчёт, а не
молча подставить дефолт.

### 10.2. Реанализ обязателен — и почему `analyze --clear` его не заменяет

Уточнение к ходившему по проекту фольклору: **сегодня `clear_durable` действительно чистит.**
`graph/engine_v2.rs:1406-1442` сносит `current.json`, `manifest_index.json`, `manifests/`,
`segments/`, `gc/` и pin-sidecar, после чего создаёт свежий манифест и скелет шардов;
док-комментарий `:1379-1405` фиксирует и crash-семантику, и фразу *«clear never silently
resurrects data»*. Плацебо-поведение, зафиксированное в старых заметках, к текущему HEAD
неприменимо — это **исправленное утверждение rev 1.0**.

Но для миграции остаётся ровно одна значимая дыра, и она структурная:

```rust
// graph/engine_v2.rs:1436-1437 — внутри clear_durable
let shard_count = self.cached_profile.shard_count;
let fresh_store = MultiShardStore::create(&path, shard_count)?;
```

`db_config.json` **не удаляется** — в списке `remove_*` его нет. Значит `shard_count` переживает
очистку. Поскольку §5.2 меняет функцию маршрутизации (`compute_shard_id(file)` →
`blake3_u64(subject) % shard_count`), а кода решардинга в дереве не существует, **фаза P6 не может
опереться на `--clear`: она требует НОВОГО каталога базы.** Это нормативное требование миграции, а
не рекомендация.

### 10.3. Конвертер

Сегодня такой утилиты нет: в `packages/rfdb-server/Cargo.toml:107-121` объявлены четыре бинаря —
`rfdb-server`, `bench_report`, `bench_lock_contention`, `bench_manifest_growth`. Конвертер — пятая
цель, отдельная от сервера (он обязан уметь работать без сети и без движка вывода).

Его обязанности, в порядке выполнения:

| Шаг | Что делает | Опирается на |
|---|---|---|

| 3 | `author` ← `_source`, `tick` ← `_generation`, `perspective` ← `main`; недостающее → `$legacy`/0, со счётчиком в отчёте | §10.1 |
| 4 | **Перетипизирует 20 709 id-значных строковых метаданных в `Value::Id`** и объявляет `source_node/2`, `handler_function_id/2`, `anchorCall/2` стратегией `Adjacency` | §2.5, MEASURED `idmeta.py` |
| 5 | Прогоняет `Functional`-разрешение (§2.3) и **эмитит `conflict/5`** на каждом расхождении вместо того, чтобы «оставить первого» | §2.3, §4.2 |
| 6 | Считает `canonical_state_sha` новой базы (§9.1) и кладёт его в отчёт вместе с четырьмя метриками §9.4 | §9 |

Шаг 5 не гипотетический. MEASURED на реальной базе:

Все 39 — это одна и та же ситуация: сущность одновременно объявлена
`GLOBAL_DEFINITION` из `<runtime/haskell>` и `EXTERNAL_FUNCTION` из

конфликт становится **фактом в базе**, который можно запросить.

### 11.3. Чем платим — честный долг

Три долга, названные не ревью, а самими артефактами.

**1. Провенанс не собирается мусором.** v0 называет это своим ограничением дословно
(`LIMITS.md:58-60`: *«Frozen provenance is never garbage-collected. Long multi-tick runs accumulate
`derived_by` history … there is no compaction»*). Модель этого документа наследует ту же
асимптотику: `derived_by` — обычный факт, монотонный рост §6 распространяется и на него, а §2.4
делает мёртвые ассершны неудаляемыми по определению. Единственный названный рычаг — архивный tier
M4 (§6.5), и его множитель **не измерен** (U-3).

**2. Рефлексивный слой живёт в одной перспективе и вне времени.** v0: *«Reflection facts live in
`[main]` and are timeless; rules do not carry per-perspective reflection»* (`LIMITS.md:52-55`).
Это значит, что §5.4a (неинтерференция по построению) **не распространяется на правила**: правило,
объявленное в одной перспективе, видно всем. Документ это не чинит и не должен — но
`E-PERSP-001` (§5.4b) охраняет только факты, не правила, и это надо знать.

**3. Запросы — god-view.** `LIMITS.md:44-45`: *«Queries are god-view. `sees`/`imports` govern the
`leak` audit, not query authorization»*. Перспективы — механизм аудита, а не изоляции. Для RFDB как
сетевого сервиса это отдельный (O-6) и НЕ решённый вопрос: авторизация чтения по перспективе в
модели отсутствует.

**4. Проза вне сети аудита.** Прогон v0 нашёл это сам и назвал точно
(`run/SUBSTRATE_ISSUES.md:56-67`): *«The graph audits what the graph holds»* — файл
`terras_table.md` семь раундов нёс устаревшую оговорку после того, как соответствующая лемма была
доказана в ядре, и поймал это не аудит, а отдельный ручной проход. Предложенное там же лечение —
`doc_note(File, NoteId)` как первоклассный факт с той же машинерией supersession, чтобы
приземлившееся доказательство поднимало `stale_note`. Отчёт прогона ставит это **первым** пунктом
рекомендаций (`run/TESTDRIVE.md:120-121`). В §2.7 `doc_note/2` включён в нормативный список
рефлексивных предикатов; `stale_note` — правило поверх него, а не отдельный механизм. **Долг в том,
что этот же дефект есть у самого Grafema**: `_ai/research/*.md` не аудируются графом, и настоящий
документ — не исключение.

И один процедурный долг, обнаруженный при верификации самого документа: **CI не запускает Rust-тесты**.

```
$ grep -c cargo .github/workflows/ci.yml
0
```

Все гейты C1–C8 §10.5 предполагают CI-исполнение. Сегодня его нет — гейт, который не запускается,
это не гейт.
