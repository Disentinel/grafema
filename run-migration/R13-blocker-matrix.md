## Почему прежние числа врали

`translate()` (`packages/rofl-conformance/src/translate.ts:148-200`) идёт по **фиксированным
фазам** и возвращает управление на **первом же** совпадении: рефлексия → перспективы → темпоральное
→ составные термы → большие числа → builtins → константы/арность. То есть для каждого падающего
кейса мы видели ровно ОДИН блокер — тот, чья фаза стоит раньше, — а не все.

Отсюда мой вывод «18 из 25 RED — это правила-как-данные». Это не факт о работе, это факт о порядке
фаз в трансляторе. Настоящий ответ: правила-как-данные — **единственный** блокер всего у **3**
кейсов.

Второй раз я ошибся уже в поправке: назвал «1–2». Измерено — **3**.

## Корневая причина такой связности

`boot.rofl` сам непереводим сразу по **четырём** линиям, и его `load()`-ят **15 из 25** RED-кейсов.
Пока `boot.rofl` не переводится, эти 15 не могут пройти ни при каком локальном исправлении.

Подлинии внутри непереводимости `boot.rofl`:

| подлиния | кейсов |
|---|---:|
| builtins | 18 |
| режим «по запросу» / несвязанная переменная в голове | 18 |
| целочисленные константы | 17 |
| перспективы / именованные | 16 |
| режим «по запросу» / небезопасное отрицание | 15 |

## Что из этого следует для порядка работ

1. Приоритет по «первому блокеру» — артефакт. Использовать ТОЛЬКО колонку «встречается» и кривую
   жадного закрытия.
2. Ближайшая цель — не «перспективы», а **ядро из четырёх линий**, потому что до него кривая
   плоская (3 → 4 → 5), а на нём прыгает до 11.
3. `boot.rofl` — узкое место всей четвёрки: он же и есть тот объект, на котором все четыре линии
   должны сойтись. Правильная единица работы — «сделать `boot.rofl` переводимым», а не «закрыть
   линию X».
